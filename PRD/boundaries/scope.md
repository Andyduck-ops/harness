# Scope & Boundaries — 范围定义与安全边界

## Harness 是什么

Harness 是一个 **AI Agent 执行环境工程系统**。

它做的事：
- 构建让 Agent 可靠产出代码的结构化环境
- 通过 Hook 在关键边界点强制注入上下文和拦截违规
- 管理知识资产（spec、lessons、ADR）的生命周期
- 定义 Agent 的权限阶梯、失败预算和求助协议
- 实现知识复利——每次任务让系统变得更好

## Harness 不是什么

| 不是 | 原因 |
|------|------|
| **不是代码生成器** | Harness 不写代码，Agent 写代码 |
| **不是 AI 模型** | 它是模型的执行环境，不是模型本身 |
| **不是项目管理工具** | 它不管 sprint、ticket、人员分配 |
| **不是 CI/CD 系统** | 它利用 CI/CD，但不替代 GitHub Actions 等 |
| **不是全自动无人系统** | 人在高杠杆点守门（P12） |

## 范围外（Explicitly Out）

| 不做 | 原因 | 替代方案 |
|------|------|----------|
| AI-to-AI 自动生成 spec | 第九轮辩论否决：可靠性 81%（0.95^4），ROI 负 | 人写 spec，AI 辅助起草 |
| 4 阶段自动门控流水线 | 第九轮辩论否决：9/30 分，735 行 = 7.35x 复杂度 | 人在 spec 审批点守门 |
| 完整的多后端调度 | myclaude codeagent-wrapper 是独立组件 | 未来作为可选桥接 |
| 跨项目知识共享 | 当前每个项目独立 | 未来通过 global skill 实现 |
| 可视化 dashboard | 过度工程化 | CLI 输出 + git log 足够 |
| 自动回滚机制 | git revert 已够用 | 手动 git revert |

## 安全边界

### "代码可抛弃" 的严格适用条件

基于圆桌辩论 5 位大师的共识，"阅后即焚" 仅在以下条件 **同时** 满足时适用：

| 条件 | 说明 |
|------|------|
| 纯函数 | 无副作用，输入输出明确 |
| 无状态 | 不依赖全局状态或历史 |
| 低失败成本 | 错误不会造成严重后果 |
| 高测试覆盖 | 有完备的验证用例 |
| 频繁迭代 | 模型升级带来的收益大于风险 |

**以下场景代码不可轻易重生成：**
- ❌ 安全/权限/支付/审计相关
- ❌ 核心算法（已优化、有性能约束）
- ❌ 分布式协调逻辑
- ❌ 状态管理（数据库 schema、缓存策略）
- ❌ 已在生产环境长期运行的代码（Lindy 效应）

### EHRB 高风险操作分类

| 类别 | 检测 | 处理 |
|------|------|------|
| **E**nvironment | 修改 .env / 配置文件 | 二次确认 |
| **H**igh-impact | 删除/重命名核心文件 | 阻塞 + 人工审批 |
| **R**eversibility | 不可逆操作 | 阻塞 + 人工审批 |
| **B**oundary | 跨越安全/网络/权限边界 | 阻塞 + 人工审批 |

### 数据安全

- 不提交 `.env`、credentials、secrets
- Hook 检测并拦截敏感文件的 git add
- API keys 通过环境变量注入，不写入任何文件

## 反模式清单

以下做法违反 Harness 原则，必须避免：

| 反模式 | 违反的原则 | 正确做法 |
|--------|-----------|----------|
| 先写代码后补 PRD | P5 | 先定义意图，再实现 |
| 把 PRD 当功能清单 | P5, P6 | PRD = 意图 + 约束 + 成功标准 |
| 只有文档同步没有验证 | P2 | 机械化强制 > 文档建议 |
| 同一 Agent 包办需求+实现+测试 | P8 | 独立验证，减少相关误差 |
| 指标被优化，真实意图被遗忘 | P5 | Goodhart 效应警告 |
| 过早求助（未收集证据就升级） | P7, P9 | 先自主探索，到预算再升级 |
| 无界重试（同一命令反复跑） | P7, P8 | 无证据重试被禁止 |
| 静默绕过（用 fallback 隐藏失败） | P8 | 严禁假成功路径 |
