# Validation Gates — 质量门与成功标准

## 设计原则

1. **不信任 Agent 的自我报告** — 所有验证用程序化外部命令
2. **验证是门禁，不是装饰** — 没有验证的需求等于未定义
3. **corrections are cheap, waiting is expensive** — 最小化阻塞门，快速纠偏

## 两级质量门控

| 级别 | 时机 | 执行者 | 机制 | 阻塞性 |
|------|------|--------|------|---------|
| **Level 1: Fast** | 每次修改后 | Agent 自行 | lint + typecheck + unit test | 非阻塞，失败立即重试 |
| **Level 2: Gate** | 阶段收束时 | quality-gate hook | 完整测试套件 + 验证命令 | 阻塞，必须通过才进入下一阶段 |

## 各阶段验证标准

### plan → implement 门

| 检查项 | 方法 | 必须 |
|--------|------|------|
| prd.md 存在且非空 | 文件检查 | ✅ |
| 成功标准已定义（SC-N 格式） | 正则匹配 | ✅ |
| 边界已定义（Always/Ask/Never） | 正则匹配 | ✅ |
| 验证命令已定义 | 正则匹配 | ✅ |
| **人工已审批** | 显式确认 | ✅ |

### implement → check 门

| 检查项 | 方法 | 必须 |
|--------|------|------|
| 代码变更存在 | `git diff --stat` | ✅ |
| 无语法错误 | lint 命令 | ✅ |
| agent-outputs/implement-result.md 已写入 | 文件检查 | ✅ |
| 未修改范围外文件 | diff vs prd.md 范围 | ⚠️ 警告 |

### check → finish 门（quality-gate hook）

| 检查项 | 方法 | 必须 |
|--------|------|------|
| prd.md 中所有验证命令通过 | 逐条执行 | ✅ |
| 无回归失败 | 完整测试套件 | ✅ |
| agent-outputs/check-result.md 已写入 | 文件检查 | ✅ |
| **Agent 必须真正运行了验证命令** | 命令执行日志 | ✅ |

### debug 循环门

| 检查项 | 方法 | 必须 |
|--------|------|------|
| debug 次数 ≤ 3 | task.json debug_count | ✅ |
| 每次 debug 策略不同 | 证据日志比对 | ⚠️ 建议 |
| 第 3 次失败 → 升级人工 | 3-Failure Protocol | ✅ |

## 3-Failure Protocol（SPARV 移植）

| 失败次数 | 处理 |
|---------|------|
| 第 1 次 | 自主重试，必须换策略 |
| 第 2 次 | 触发 debug agent，聚焦根因分析 |
| 第 3 次 | **停止自主执行**，结构化求助，提供 A/B/C 选项 |

**关键：失败计数不因策略切换而重置。** 衡量的是"当前任务的整体困难度"，不是"单个策略的尝试次数"。

## 北极星指标

| 指标 | 定义 | 目标 | 计算方式 |
|------|------|------|----------|
| **ICR** | Intent Coverage Ratio | ≥ 80% | 有验证的 Intent / 全部 Intent |
| **ASR** | Agent Self-Resolution Rate | ≥ 70% | 无人工介入完成的任务 / 全部任务 |
| **KCR** | Knowledge Compound Rate | ≥ 0.3 | 可复用教训数 / 完成的任务数 |
| **DDL** | Drift Detection Latency | ≤ 1h | 意图变更到全链路一致的中位时长 |
| **BER** | 需求误码率 | ≤ 5% | 错误/遗漏实现 / 全部实现 |
| **MTTR-D** | 漂移修复时长 | ≤ 4h | 发现不一致到修复的中位时长 |

## 验证的局限性（圆桌辩论共识）

这些门控提升可靠性，但不能替代理解：

- **测试只能证伪，不能证真**（Lamport）
- **未知的未知无法被测试捕获**（Taleb）
- **本质复杂度无法被门控消除**（Brooks）

因此：
- 高风险路径（安全/支付/权限）需要额外的人工审查
- 生产环境的 Lindy 证据（已运行的代码）不可轻易抛弃
- 验证命令的质量本身需要被审查——Goodhart 效应警告
